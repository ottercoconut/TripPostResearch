## 一、目的与使用范围

为每个已确定为keep的post生成有序的`text_segments`，作为该post记录内的JSON数组，保留片段原文、编号和位置。原正文不变，不为每个片段另建帖子记录。

总原则是：**标点决定基本边界，结构规则避免误切，原文与位置始终可追溯；评价单元另按上游要求检查。** 不按字数硬切，不按编码员的临场阅读习惯切，不依赖大模型逐帖自由裁量。

本规则明确区分两种完成程度，不能混称：

- **基础片段**：完成下文R01—R09与完整性检查，可供管理端预览、检索和切分审阅；不能据此宣称符合正式V3—V6观察单位。
- **正式编码片段**：还必须满足R10评价原子要求，通过既有共同校准、边界裁决和冻结门。实现R01—R09而尚未完成R10时，整个运行必须标注为仅供试用，不因“程序没有报警”变成正式可编码。

这些是同一任务的成熟度区分，不是本次新增两套业务表。若后续边界改变，须生成新切分版本，不能让旧编码证据继续引用已经换义的编号。

## 二、输入与存储契约

### 2.1 唯一输入正文

1. 当前输入固定为keep成员关联的冻结源快照`web_posts.content_text`，以post身份、来源快照、来源版本确定唯一记录。keep表示成员经过筛选，不代表正文不存在HTML实体、装饰行或格式残留。
2. 单独的`title`仅作上下文，不再次拼到正文前；如果`content_text`已经含有标题，不自动去重或删除。标题单独参与切分须另行定义输入投影，不能静默改变当前坐标。
3. 不修改原文的全半角、简繁体、错字、大小写、空格、HTML实体、表情、标签或换行。不把`\r\n`改写成`\n`之后仍沿用旧位置。
4. 不从图片、OCR、外部页面或作者资料补正文；不将正文缺失的post擅自改为exclude。

### 2.2 JSON字段

字段名沿用本轮约定的`text_segments`。SQLite中使用可为空的`TEXT`保存JSON数组；具体迁移、写入事务和管理端权限不属于本文件。

| 成员字段 | 类型 | 约束 |
|---|---|---|
| `seg_id` | 正整数 | 在该post的该切分版本内从1连续递增，按原文顺序排列 |
| `raw_text` | 字符串 | 必须等于输入正文的`source_text[start:end]`，不插字、不改字 |
| `start` | 非负整数 | 原始输入正文中的起点，包含该字符 |
| `end` | 正整数 | 原始输入正文中的终点，不包含该字符；必须大于start |

位置统一按**Unicode码点、从0开始、左闭右开**计算，不是UTF-8字节，也不是JavaScript UTF-16字符串索引。前端高亮必须做坐标转换，不能直接拿含emoji正文的`String.slice(start,end)`当等价操作。组合emoji在边界识别时必须整体处理，位置仍按原始码点计数。

`NULL`表示尚无可用切分结果，可能未执行或执行失败，具体状态查运行记录；`[]`仅表示成功检查后没有可切分的非空白正文。失败不能伪装成`[]`。缺正文而只有标题的情况须记录`EMPTY_BODY`，不生成`[EMPTY]`等伪造片段。

一个字段仍可保留简洁数组；但运行manifest必须逐post绑定输入正文SHA-256、来源身份、规则/程序版本、输出SHA-256和问题记录。不得只留一个脱离运行谱系的数组。`post_id + seg_id`仅在指定切分版本内唯一，长期引用须带来源版本及切分运行标识。

### 2.3 保留与空白

只允许将候选片段两端的明确空白留在片段间隙，不得去掉片段内部空白。空白集合固定为Unicode White_Space集合：U+0009—000D、0020、0085、00A0、1680、2000—200A、2028、2029、202F、205F、3000；此集合写入规则配置。

U+200B、U+200D、U+FEFF等不在此集合中，不作为普通空白丢弃；保留并在需要时提示`FORMAT_CHARACTER`。尤其不能删掉emoji中的连接符。片段以外只能留下上述空白，每个非空白码点必须且只能被一个片段覆盖。

## 三、基础规则

### R01：先识别受保护的文字，不在其内部切分

下列完整文字单元先定位到原文区间，内部即使出现标点也不直接切：

- HTML实体形式，如`&#34;`、`&#x22;`、`&amp;`。其末尾`;`不是句末。只保护，不解码；不能把实体中的`#`识别成话题开头。
- 带`http://`、`https://`或`www.`前缀的链接、形态明确的邮箱。链接查询参数中的`?`、`;`、`!`不作句末；内部的`#`不作话题。
- 数字中的小数点、时间中的冒号、按R05识别的完整列表标记。标记识别先于符号配对：例如`1)`的右括号属于编号，不能记作未闭合括号；此时只标记区间，最终列表边界稍后裁决。
- 完整平台表情标记，例如合成示例`[笑脸R]`，以及完整Unicode组合emoji。

链接区间从显式前缀开始，到空白、中文句末标点或外层结构分隔符前结束；不能吞掉引号、括号的外层闭合符号。ASCII `? ! ;`既可能是链接尾部也可能是句末，无法唯一确定归属时保留该链接候选整体并登记`URL_BOUNDARY_AMBIGUOUS`，不得靠猜测截断链接。全角/ASCII括号的归属由R03配对决定；不认识的裸域名不自动扩展成链接。

链接候选直接粘连中文正文或栏目编号、不能唯一恢复边界时同样报警并保留整个候选；不能用某一平台的ID长度猜数字链接的最后一位是否其实是下一列表序号。

### R02：强标点形成基本边界，连续强标点只算一次

| 类型 | 字符或形式 | 处理 |
|---|---|---|
| 强标点 | `。！？；`及ASCII `!?;` | 在整组末尾生成一个候选边界，符号归前一片段 |
| 连续强标点 | `！！！`、`？！`、`。。`等 | 连续的一整组保留，不把第二个标点切成新片段 |
| 普通分隔符 | `，,、：:` | 不作为通用句界；列表与R10另行处理 |
| 省略/补充符号 | `…`、`……`、连续ASCII点、`—`、`——`、`～~` | 不作为通用句界 |
| 普通空格 | 包括多个空格 | 不作为通用句界 |
| 像标点的emoji | `❗❓‼⁉`及其变体 | 按emoji保留，不自动等同`！？` |

**英文句点`.`采用保守而明确的例外规则**：R01保护之后，非连续点中的单个`.`，仅当后面是空白、正文结束或闭合引号/括号时，作为候选句末；通过R03检查后决定实际边界。列表编号、已识别小数、链接和邮箱中的点不得触发。一个物理行去掉两端空白后仅有`.`或连续点时按装饰行保留，不生成空片段。

英文常见缩写的例外集合必须随实现版本固定，不能运行时自学习；初始候选集合为`Mr.`、`Mrs.`、`Ms.`、`Dr.`、`Prof.`、`Sr.`、`Jr.`、`St.`、`vs.`、`etc.`、`e.g.`、`i.e.`，匹配大小写不敏感且要求词边界。多段单字母缩写（如`U.K.`）和人名首字母形式也先保护。缩写是否恰处于句尾无法由规则确定时登记`ASCII_PERIOD_AMBIGUOUS`，不自动补边界。该集合是新工程选择，尚未通过本次50条的独立验证。

### R03：引号、括号成对处理，闭合符号不甩到下一段

1. 成对识别`“”`、`‘’`、`「」`、`『』`、ASCII单双引号，以及`（）`、`()`、`【】`、`[]`；按正确嵌套配对。书名号`《》`、`〈〉`采用与括号相同的整体保护。英文单词内部、两侧均为字母或数字的ASCII单引号不作为引号开闭。
2. 引文内部的强标点和换行暂不生成普通边界，整段引用作为受保护区域；内部评价属性/方向的变化仍受R10约束，不享有绝对豁免。
3. 引文最后一个非空白内容字符是按R02判定的句末标点时，将句末候选边界移至闭合引号及紧随其后的句末标点之后。若之后的下一个非空白字符是逗号、顿号或冒号，取消这个引文末候选边界，继续保留其归属句。嵌套引用的候选边界仍不能穿透尚未闭合的外层引用或括号。引文前的引述语随首段保留，不单独拆成“他说：”。
4. 括号中的补充说明整体保留在当前句内；不因其内部强标点产生外层句界。外层的句末标点、换行或列表边界仍可切。因此`行程（很好！）继续。`保持一段，`行程（很好！）\n返程。`形成两段。
5. 不得生成由程序误切造成的孤立右引号、右括号；原文本来单独一行的异常闭合符号则保留并报问题，不能静默删除。
6. 未配对或交叉配对的符号记`UNBALANCED_DELIMITER`，不补字、不配对到不匹配的符号；未配对起始符号不享有“保护余下整帖”的权限。按其他基础边界生成预览，并保留问题供裁决。

### R04：换行是结构边界，空行不产生空片段

- R01/R03保护区域外，CRLF视为一个换行事件，单独CR、LF及Unicode行/段分隔符U+2028、U+2029也作为结构边界。原始字符与位置不改写。
- 普通非空行独立处理；空白行跳过，不生成片段。
- 一行内有多个句末标点时，仍按R02继续切分。不能将“一个物理行”和“一个片段”混为一谈。
- 换行前没有标点，或以逗号结尾，也可以形成结构边界；不因下一行语义承接便临时合并。
- 只有R03确认的成对引文/括号可以跨行保护。诗性排版但无引用结构时按行切，不用内容猜测把几行重新组诗。

### R05：明确列表项独立，路线节点不逐个拆

识别以下列表形态，列表标记归后面的条目，条目内部仍适用其他规则：

1. 行首的`1.`、`1、`、`1)`、`1：`、`①`、`一、`、数字键帽emoji，以及独立项目符号`· - •`。编号紧邻的前置emoji装饰（如`📍 Day1`）归入该条目，不甩给上一段；字母内部的数字或图号不充当编号。
2. `Day1`、`Day 1`、`D1`、`第1天`等行程标记，后接冒号、空白或路线内容；ASCII字母大小写不敏感。行首一个完整标记即可成为条目起点。
3. 无换行的正文中，只有**至少两个同系列、递增的明确标记**才能触发行内列表识别。例如`D1：…D2：…`、`1、…2、…`；每项须有非空内容。数字/Day前缀不能位于英文单词内部。
4. 行内ASCII`1.`须额外满足点后不是数字、不是缩写/链接/版本号的一部分，且与后续编号形成同系列证据；`1.5小时`不能当条目。证据不足登记`LIST_BOUNDARY_AMBIGUOUS`，不拆。
5. `Day1：A→B→C`中的箭头表示同一项内的路线，不把A、B、C分别切开。单独的`-`也不是路线通用分割符。

数字冒号标记同样适用递增系列证据；冒号后紧接数字的时间（如12:30）不是列表。

嵌套列表按同系列分别检验，不因Day条目夹在1./2.之间便丢失父层编号。中文“第一天/第二天”与阿拉伯天数采用同类处理。层级编号如4.1/4.2，只有“编号+空白+短标题+冒号”且同父级有递增证据时才作为行内边界，小数和日期不因此变成列表。

列表前的非空标题/引导文字不能凭空消失：例如`行程：\nD1：A\nD2：B`保留“行程：”和两条行程，共三段。本候选采用**保留独立标题段**，不同于旧报告中省略展示标题的三日行程示例；采纳时应将示例同步写清，不能一面要求完整覆盖，一面实际丢弃标题。

### R06：表情按其原始位置归属，不拆组合、不推断含义

- 原文独立一行的纯表情作为一段，连续几个emoji不逐个分段。
- 同一行的句末强标点后，若直到行末/正文末只有表情及空白，则该表情尾缀随前一句保留，句界延后到尾缀末尾。例如`出发！！🌊`为一段。
- 上一项只适用于可由固定Unicode规则或平台标记确定的纯表情尾缀；若后面还有文字，表情留在其原有连续区间中，不凭语义猜测属于前句还是后句。
- 同行内部emoji不是通用边界。不得删除变体选择符、肤色修饰符或零宽连接符，不把组合emoji截断。
- 单靠ASCII或`\w`正则不能穷尽Unicode装饰/表情。实现须固定Unicode数据版本及完整组合识别方式；未知符号保留，不能因为分类失败丢字。

### R07：纯标签块保留，明显前后缀可与正文分开

1. 完整成对话题`#主题#`，以及以空白/行末结束的单端话题`#主题`，按完整token识别；`#`后立即为空白不是话题，受R01保护的`#`不参与识别。
2. 多个相邻话题及其间空白作为一个标签块，不按每个`#`切开。紧连的`#甲##乙#`按两个完整token识别，仍属于一个标签块。
3. 标签块独立成行时为一段。标签块位于某一行明确的前缀或后缀时，也建议与该行正文分开，即使没有句号；这项是对旧报告“纯标签行”的**拟新增工程约定**，尚未生效。
4. 文字内部嵌入的标签先保留在当前片段，无法确定词组范围时登记`TAG_BOUNDARY_AMBIGUOUS`，不把剩余整句吞成标签。无空白且无闭合`#`的“话题+正文”不做猜测性拆分。
5. 独立的`@提及`行作为一段；非独立提及保留原处，不能从显示名中的空格推断任意截断位置。

单端话题之间的“空白+#”不得被错认为前一个话题的闭合。正文后直接粘连的单端标签，至少有两个完整、空白分隔的尾部token才按整块分出；只有一个、又缺少闭合符号时保持预览并提示。标签之间和标签块首尾的U+FEFF/U+200B可作为结构桥接字符归入标签块，但必须原样保留在raw_text中，不能当空白删除。

标签间的逗号/顿号也可作为标签块内的连接符，保留不另起段。若共用井号或单双端混合使标签闭合不唯一（如#甲#乙#丙），在没有强句末的尾部范围内整体保留并登记TAG_SYNTAX_AMBIGUOUS，不硬拆成“部分标签+伪正文”。这属于显式回退，不等同已恢复真实标签结构。

### R08：极短段、装饰行、长段均不按长度自动修补

- `赞！赞！赞！`按三个句末切为三段；`免费！出发！`为两段。短段有无独立语义不由长度阈值决定，连续字符重复也不触发通用合并。
- 独立的`.`、`-`、`·`、波浪号或花纹装饰行保留为一个片段，并可登记`DECORATION_ONLY`。不默默删除，也不因此改写清洗结论。
- 缺少可靠边界的长段保留完整。超过200码点只记`LONG_SEGMENT`供审阅，该200是沿用临时探针的提示值，不是正确性阈值或模型截断限制。
- 很长的标签块不因长度被拆成几份。模型将来需要token窗口时使用独立推理窗口映射，不修改本层`seg_id`。

### R09：在所有基础边界处理完成后才编号

先定位结构、收集与裁决边界，再生成片段；禁止一边逐条替换原文，一边累计位置。最终区间按照原文排序，编号从1开始；使用明确空白集合修剪片段边缘并相应移动start/end，不调整原文。

冲突处理顺序固定为：

1. 识别不可拆文字单元及配对结构；
2. 生成句末、换行、列表、标签块边界候选；
3. 删除受保护区域内不应生效的基础候选；
4. 处理引文闭合、连续句末标点与同行表情尾缀；
5. 处理R10适用的评价边界及未解决问题；
6. 排序、去重、生成区间并编号，执行完整性检查。

列表和标签识别不能穿透链接、实体、引用或括号。编号后不得由管理端单独拆并片段；争议记录在运行问题清单，规则修订后统一重生成。

## 四、R10：正式编码前必须满足的评价原子要求

本节保留编码表已有约束，不把它伪装成一种标点：

- 评价或建议从一个V6属性转向另一个属性时切分。
- 同一属性正负方向改变，或不同属性分别承载不同方向时切分。
- 同一属性、同一方向的并列、程度补充或递进描述，不**额外**按逗号、连接词拆分；不因此撤销已经成立的独立句末边界。
- 一般知识、活动或内容策略共现不是切分理由；“出现多个标签词”不等于存在多个评价原子。

连接词只是定位线索，**不得见到“但、还、更、而且、然后”就全部切开**；“虽然……但是”也不是不切分的绝对豁免。建议统一处理程序先确定候选分句及属性/方向证据，再裁决边界，不让编码员各自改段。

边界落在连接词前；前面的逗号/顿号归前段，连接词归后段，不能为了让例句好看而删掉连接词。无标点时若规则可唯一定位后一个评价表达的起点，才使用该起点。一次源区间只能归一段，不重复复制省略的评价对象。

合成示例：

- `海湾很美，但停车不方便。` → `海湾很美，` / `但停车不方便。`
- `收费偏高，不过总体值得。` → `收费偏高，` / `不过总体值得。`
- `人很多，排队也很久。` → 一段；不能仅因“也”机械拆分。
- `大厅整洁、没有异味。` → 一段。

引用中的同类切换也需要拆；开引号留在第一段、闭引号留在最后一段，允许两个评价片段分别持有引用结构的首尾，但不能丢掉引用字符。

**当前未解决的实现边界必须如实记录**：仅凭本文件或50条抽样，不能认定版本化的属性线索、评价谓词、否定作用域、反讽及省略规则已经完整实现。无法唯一判断时保持基础预览结果并登记`UNITIZATION_PROBLEM`，不得把这个回退当成已通过正式编码验收。尚无完整R10实现与验证时，整批不能发布为正式编码片段。

如果最终选择“管理端和研究永远只按标点切”，那是对现有编码单位的研究决策变化，须另经用户确认并同步修订编码表，不能由本文暗中替换。
