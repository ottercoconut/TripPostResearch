## 一、问题背景

### 1.1 为什么需要片段级编码

本研究的文本轨采用**片段级编码**而非帖子级编码，核心原因有三：

1. **消除帖子长度的混杂效应**：帖子越长，命中的标签种类越多——这是长度驱动的伪共现，而非创作者的策略选择。片段级编码下，密度指标（命中数/片段数）自动对长度进行标准化。
2. **候选共现分析的信效度**：如果编码表未来解除SRM、SAM等聚合指标的`DEFERRED`状态，片段级证据可降低帖子长度导致的伪共现；这些指标当前不是切分或模型训练的前置条件。
3. **模型训练的技术优势**：短文本的标签-证据对应关系更直接，多标签分类在短文本上的表现通常优于长文本。

### 1.2 切分标准的必要性

候选文本轨聚合指标可能使用`segment_count`作为分母；即使这些指标当前为`DEFERRED`，训练与信度评估的基本观察单位仍依赖稳定切分。如果切分实现不固定：

- 不同标注批次可能得到不同`seg_id` → 信度计算的单位不可比
- 规则或程序版本漂移 → 训练、开发和锁定测试集的观察单位不一致
- 编码员自行改边界 → 同一`seg_id`不再对应同一证据片段

因此，确定性程序必须在标注开始前按同一规则版本预先生成并固定`seg_id`。当前文本轨已达到共同校准准备状态；共同校准可使用固定`seg_id`，但独立盲试标和正式任务仍受编码表冻结门约束。

## 二、设计原则

| 原则 | 说明 |
|------|------|
| **P1 可操作性** | 基本边界使用标点、换行和连接词；评价对象或情感方向切换按上位编码表的评价原子规则处理，并由统一程序生成，不交给编码员临场决定 |
| **P2 可复现性** | 同一原始文本、清洗版本和规则版本必须由程序生成完全相同的片段边界与`seg_id` |
| **P3 语义粒度合理** | 切出的片段应适合做共现分析——既不过粗（一个片段混杂多种策略），也不过细（把一个语义单元拆成碎片） |
| **P4 尊重作者标点** | 程序按规则处理原作者标点；编码员不决定“哪里该断句” |
| **P5 宁合不拆** | “宁合不拆”是程序的确定性回退规则，不是编码员的自由裁量；疑难输入进入问题队列，但当前边界保持不变 |

## 三、核心切分规则

### 3.1 规则一：句末标点为主边界

以**句末标点**作为片段的主要切分边界。

| 标点符号 | 处理方式 | 理由 |
|----------|----------|------|
| 句号（。） | **切分** | 标志一个完整命题或言语行为的结束 |
| 感叹号（！） | **切分** | 标志一个完整的情感表达或感叹的结束 |
| 问号（？） | **切分** | 标志一个完整提问的结束 |
| 分号（；） | **切分** | 前后通常是独立的命题、评价或并列陈述 |
| 逗号（，） | **一般不切分** | 逗号通常连接同一语义单元；若触发规则七的评价对象或方向切换，则必须切分 |
| 冒号（：）后接完整句子 | **不切分** | 冒号引出的解释性从句与前文构成一个语义单元 |
| 冒号（：）后接列表 | **见规则三** | 列表项独立成片段 |
| 省略号（……） | **不切分** | 通常连接同一语义单元的省略部分 |
| 破折号（——） | **不切分** | 通常连接补充说明，与前文构成一个语义单元 |

**示例**：

```
原句："栈桥始建于1892年，傍晚海风吹过来很舒服。"
→ 1个片段（逗号不切，句号切）
→ cs_edu=1, cs_emo=1（知识+氛围共现）
```

```
原句："栈桥始建于1892年。傍晚海风吹过来很舒服。"
→ 2个片段
→ 片段1：cs_edu=1  片段2：cs_emo=1（无共现）
```

两种切分结果都是合理的，区别在于原作者是否用句号将两件事断开。

### 3.2 规则二：转折连接词为次边界

当文本**无句末标点**但包含明确的转折或并列连接词时，以连接词前为片段边界。

**触发切分的连接词**（转折/递进/并列）：

| 类型 | 连接词 |
|------|--------|
| 转折 | 但是、但、不过、可是、然而、可惜、遗憾的是 |
| 递进 | 而且、并且、还、更、甚至 |
| 并列 | 另外、还有、同时、此外、一方面…另一方面 |
| 顺承 | 然后、接着、随后、之后 |

**不触发切分的连接词**：

| 类型 | 连接词 | 理由 |
|------|--------|------|
| 因果 | 因为…所以、因此、于是 | 前后构成一个完整的因果论证 |
| 条件 | 如果…就、只要…就 | 前后构成一个完整的条件句 |
| 让步 | 虽然…但是 | "虽然"引导的从句不独立成段，与"但是"后的主句合并 |

**示例**：

```
原句："门票80有点贵但是风景真的美到窒息"
→ 切分点在"但是"
→ 片段1："门票80有点贵" → cs_inf=1, at_has_eval=1, asp_pri=1
→ 片段2："风景真的美到窒息" → cs_emo=1, at_has_eval=1, asp_res=1
```

```
原句："因为是淡季所以人很少体验很好"
→ 不切分（因果连接）
→ cs_inf=1, at_has_eval=1, asp_cro=1
```

### 3.3 规则三：列表项独立成段

攻略帖中常见的列表结构，每项独立为一个片段，即使没有句末标点。

**识别标准**：冒号或换行后，以以下任一方式分隔的独立攻略项：
- 编号（1. 2. 3. / ① ② ③ / 一、二、三、）
- 项目符号（·、-、•）
- 换行符（每个独立行）
- 箭头序列中的独立节点（Day1→A→B 中的 A 和 B 属于同一项）

**示例**：

```
原帖：
"青岛三日游攻略：
Day1：栈桥→天主教堂→信号山
Day2：崂山一日游
Day3：啤酒城→金沙滩"
```

→ 3个片段（Day1、Day2、Day3各为一个片段）

```
原帖：
"推荐几个必吃：
· 海鲜大排档（人均80）
· 青岛啤酒（原浆最正宗）
· 烤鱿鱼（台东夜市）"
```

→ 3个片段（每个推荐项独立）

### 3.4 规则四：对话/引用整体成段

直接引用、对话、转述整体作为一个片段，不在引号内部切分。

```
原句："我问老板'这个多少钱'，他说'30块随便吃'。"
→ 1个片段（整段对话）
```

### 3.5 规则五：纯表情/纯标签独立成段

独立的emoji行、话题标签行、@提及行作为单独片段。

```
原帖：
"崂山日出太震撼了！！！
🔥🔥🔥
#崂山日出 #旅行打卡"
```

→ 3个片段：
- 片段1："崂山日出太震撼了！！！" → cs_emo=1, rs_n_geo=1, rs_n_cli=1
- 片段2："🔥🔥🔥" → cs_oth=1, at_non=1
- 片段3："#崂山日出 #旅行打卡" → cs_oth=1, at_non=1

### 3.6 规则六：无标点且无连接词的长句原则上不切分

当文本既无句末标点也无转折连接词，且未触发规则七的评价对象或方向切换时，不切分。

```
原句："门票80有点贵风景也很美"
→ 2个评价原子片段："门票80有点贵" / "风景也很美"
→ 价格与资源品质属于不同评价对象，触发规则七
```

“宁合不拆”只用于没有明确评价对象/方向切换证据的回退情形，不能覆盖V5—V6正确配对所需的评价原子切分。

### 3.7 规则七：评价对象或情感方向切换时强制切分

为保证V5情感与V6属性在同一`seg_id`内正确配对，只要相邻分句出现以下任一变化，就在变化处生成边界，即使原文只使用逗号、空格或省略标点：

1. 评价对象从一个V6属性切换到另一个属性，如“景色很美，服务很差”；
2. 情感方向从正向切换为负向或反向切换，如“风景很美，但管理很差”；
3. 建议对象从一个目的地属性切换到另一个属性。

同一属性内部的程度补充、原因说明或不可拆分的矛盾立场不切分；此时才允许在同一片段中保留`MIX`。程序须使用版本化的评价谓词、属性线索与转折标记规则统一处理；无法确定是否切分的输入保持当前程序结果并登记`UNITIZATION_PROBLEM`，编码员不得自行改边界。

## 五、切分操作流程

标注批次导出前，由确定性预处理程序统一完成切分：

```
步骤1：读取不可变的帖子文本、清洗版本和切分规则版本
         ↓
步骤2：按规则一，在所有句末标点（。！？；）处生成切分点
         ↓
步骤3：按规则三识别列表结构，为每个独立列表项生成切分点
         ↓
步骤4：按规则二，检查是否有无标点但含转折连接词的长句，
       在连接词前生成切分点
         ↓
步骤5：按规则四、五，处理对话引用和纯表情/标签行
         ↓
步骤6：按规则七检查评价对象与情感方向切换，生成评价原子边界
         ↓
步骤7：按原文顺序为每个片段分配seg_id（从1开始递增）
         ↓
步骤8：固化raw_text、字符边界、规则版本和来源文本校验信息
         ↓
步骤9：生成标注任务；编码员审计但不得修改边界或seg_id
```

若审计发现疑似错误，编码员只提交问题记录。任何规则变更都必须先在上游编码表中裁决，再升级切分规则版本并对受影响批次整体重生成；不得直接修补单个编码员手中的片段。

## 六、与编码表的衔接

### 6.1 编码员职责

- `seg_id`及边界由确定性程序在标注前预先固定，不由编码员生成
- 编码员只核对片段是否符合可见规则，并记录`segmentation_issue`及说明
- 两位编码员面对同一批次必须编码完全相同的`seg_id`，**不得自行改变边界**
- 边界争议进入审计队列；只有编码表上游裁决和规则版本升级才能改变后续批次

### 6.2 程序确定性与人工审计

不再让两位编码员独立切分，因此不计算“编码员切分一致性”作为当前质量指标。试运行阶段验证以下内容：

| 检查项 | 计算方式 | 当前要求 |
|--------|----------|----------|
| 重复运行一致性 | 同一输入与规则版本重复运行，比较边界、`seg_id`与输出校验值 | 必须100%一致 |
| 批次内唯一性 | 检查`post_id + seg_id`唯一、连续且顺序稳定 | 必须100%通过 |
| 原文可追溯性 | 拼接片段及记录的边界能够回指来源文本 | 必须100%通过 |
| 规则符合率 | 对预注册边界案例执行回归测试 | 必须100%通过 |
| 人工审计问题率 | 抽样审计中被记录为疑似错误的片段或帖子比例 | 描述性报告；阈值待冻结 |

### 6.3 切分与编码的分离

切分和编码应作为**两个独立步骤**执行：

1. **第一步：程序切分** → 在标注导出前产出并固化`seg_id`列表
2. **第二步：人工审计** → 编码员记录问题，不改变任何边界
3. **第三步：内容编码** → 在同一批固定`seg_id`上标注编码表规定的字段

这样做的好处：
- 避免编码员在编码过程中“顺便”调整切分，确保所有人工证据使用相同观察单位
- 将程序确定性、边界审计与内容编码信度分开报告
- 训练、开发与锁定测试集复用同一切分实现和规则版本，避免数据单位漂移

### 6.4 结构化编码中的语境单位与观察单位

编码表v3.16.0允许编码员为消歧阅读完整帖子及必要图文语境，但不改变固定片段的观察单位：

- 结构化文本标签仍落在单个固定`seg_id`，证据位置须指向该片段的冻结规范文本；
- 标题、前后片段、话题标签或配图只能帮助判断代词、省略、反讽等语境含义，不能把目标片段未表达的内容追加为标签；
- 若一个含义只能跨片段成立，编码员按现行规则逐片段判断，并登记`CONTEXT_DEPENDENCE`，不得自行合并、拆分、重排或改写片段；
- 若切分规则持续造成同类意义损失，登记`UNITIZATION_PROBLEM`并进入编码簿版本评审；新规则生效前不得静默修补；
- 校准问题记录不改变`segment_count`、正式标签观察单位或模型训练样本。

## 七、对聚合指标的影响

切分标准直接决定`segment_count`，并影响训练观察单位以及未来可能启用的密度指标。在论文方法论或数据附录中需要报告：

| 需报告的指标 | 说明 |
|-------------|------|
| 样本片段长度分布 | 均值、中位数、标准差、最大值、最小值 |
| 每帖片段数量分布 | 检查确定性规则是否在特定文本形态下产生异常细分或合并 |
| 片段数的平台差异 | 不同平台的帖文风格可能导致切分数量的系统性差异 |
| 程序与规则版本 | 确保训练、开发、测试及正式推理使用同一实现 |
| 人工审计问题率 | 见6.2节；只记录问题，不在标注任务内修改边界 |

如果程序检查失败或人工审计发现系统性问题，需要：
1. 分析问题模式（是标点规则、列表识别还是输入规范化问题？）
2. 补充边界案例到裁决表
3. 先在编码表裁决涉及研究规则的变更，再升级程序与规则版本
4. 对受影响批次整体重生成并出具差异清单，不能由编码员局部修补
5. 重新通过确定性检查后，才可生成新的标注任务

---

## 八、确定性程序实现与切分模型边界

当前切分由规则程序完成，不是机器学习预测任务。BERT等模型只接收已经固定的`seg_id`，不能学习或修改边界。

### 8.1 当前程序策略

1. **规则切分**：程序严格实现本报告规则1—7，并记录实现版本
2. **预先固化**：在生成标注任务前固定边界、`seg_id`、原文位置与校验信息
3. **人工审计**：编码员只记录疑似错误，不修正当前任务
4. **回归验证**：用裁决表和已确认边界案例验证程序输出

### 8.2 注意事项

- 当前不训练、不比较也不部署学习式切分模型
- 编码员没有“自己的切分逻辑”，也没有更改程序输出的权限
- 训练集、开发集、锁定测试集和正式推理必须来自同一规则与程序版本
- 若未来提出学习式切分模型，必须先修改编码表解除当前边界；在此之前一律视为`DEFERRED`

## 附录A：社交媒体文本的标点使用特征

社交媒体文本的标点使用与规范书面语存在显著差异，切分标准需要适配这些特征：

| 特征 | 示例 | 切分处理 |
|------|------|----------|
| 连续感叹号/问号 | "太美了！！！""真的吗？？？" | 作为单个句末标点处理，不因数量增加而切分 |
| 无标点长句含转折词 | "今天去了栈桥人超多但是海很蓝" | 按规则二在“但是”前切分 |
| 标点混用 | "这个地方、真的、太美了" | 顿号按逗号处理，不切分 |
| 表情替代标点 | "太美了😍😍😍海风也很舒服" | 表情不作为切分边界 |
| 空格断句 | "推荐 必去 冲" | 空格不作为切分边界 |
| 英文标点 | "So beautiful! Must go!" | 英文句号/感叹号/问号按中文对应标点处理 |

## 附录B：与问题清单的对应关系

历史《编码表问题清单与优先级》曾将“文本片段切分规则未确定”列为P0。编码表v3.16.0继续采用确定性基本规则，并沿用v3.8.0加入的评价对象、属性指向或情感方向切换时强制评价原子切分；该历史清单不再是现行权威来源。

本报告将编码表v3.16.0的上游规则细化为确定性程序要求：句末标点为基本边界；逗号一般不切，但目的地属性指向改变、同一属性的情感方向改变，或不同属性分别承载不同情感方向时，即使只由逗号、顿号或转折连接词衔接也必须拆分；相同属性、相同方向的并列修饰或递进描述不切分。列表项、纯表情和纯标签独立成段，对话/引用仅在内部没有上述切换时整体成段。完整帖子是消歧语境，不是新的标签观察单位。V4活动资源重构不改变切分规则，但`REC/EVT`边界须在共同校准中检验；当前`NOT_FROZEN`还来自`at_eval_subtype`、校准后字段专门规则和视觉冻结门，而不是允许下游自行重定规则。

当前共同校准包使用`pilot-segmentation-v0.1`生成固定`seg_id`。该版本只证明基本边界已可供本轮审计，不代表评价原子规则已经完成独立验证；若共同校准发现其未执行上述强制拆分，须升切分内部版本、重新生成受影响任务包，且不得沿用旧`seg_id`进入盲试标或正式标注。
